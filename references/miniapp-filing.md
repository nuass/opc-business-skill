# 小程序备案与上架（微信小程序）

## 0. 先分清两种「备案」

| | 网站 ICP 备案 | 小程序备案 |
|---|---|---|
| 在哪办 | **云厂商**的备案控制台（阿里云/腾讯云/火山…） | **平台侧**：微信公众平台 / 支付宝开放平台后台 |
| 依赖 | 域名 + 境内 ECS | **不依赖服务器，也不依赖域名** |
| 关系 | 见 `icp-filing.md` | 与云账号完全无关 |

⚠️ **云厂商的备案文档里根本不出现「小程序」**（只覆盖网站与 App）。
所以"我在阿里云备过案了，小程序是不是就不用备了"——不是，两件事。
反过来，小程序**后端 API 用的域名**要单独做网站 ICP 备案，那才是云厂商那边的事。

## 1. 上架四步，顺序有硬依赖

```
① 小程序信息（名称/头像/简介/简称）
      ↓
② 小程序类目           ← 卡点通常在这里，见 §2
      ↓（①② 都完成才能提）
③ 微信认证（企业主体 + 对公打款验证）
      ↓
④ 小程序备案           ← 可与开发并行，上架前完成即可
      ↓
   提交审核 → 发布
```

- ①②③ 是**串行**的，④ 可以和开发并行跑，**但没备案不能上架**。
- 认证要走对公打款小额验证（一笔几毛钱的打款，回填金额）⇒ **必须先有对公户**。
- 存量小程序的备案有过渡期安排，**以平台通知为准**，别按传闻的日期倒排。

## 2. 真正的卡点：执照经营范围 → 类目 → 接口能力，是一条三级依赖链

这是小程序这条线**最容易低估**的地方：

```
营业执照经营范围（有没有那个关键词）
    ↓ 决定
小程序服务类目（能不能提上去、要不要额外资质证）
    ↓ 决定
接口能力白名单（某些能力只对特定类目开放）
```

举个真实形状：想做**实时视频**（`live-pusher` 一类），发现该能力只对某几个类目白名单开放；
去提那个类目，类目页要核验营业执照经营范围里的对应关键词；回头查执照，
**一个相关关键词都没有** ⇒ 整条链第一环就断了，得先去 e窗通做经营范围变更（见 `gongshang.md`）。

⇒ **正确的推导方向是反的**：先确定要做的功能 → 查它要什么类目 → 查该类目要什么经营范围/资质 →
最后才决定要不要动执照。**不要先改执照再猜类目能不能过。**

### ⚠️ 有关键词 ≠ 能过类目：小心括号里的排除性表述

经营范围的标准表述经常自带括号排除项，例如某条目写「…（不含教育培训）」。
这种条目**字面上有教育两个字，但恰好把类目要核验的那部分排除掉了**。
⇒ 拿到新执照后**别假定类目就能过**，先去类目页看它到底要什么证，再决定要不要第二轮增项。
优先试**不需要额外资质的子类目**（"信息服务/其他"一类），比硬碰要许可证的子类目省事。

## 3. 三种备案类型：改名走「变更」，不是重新备案

官方（`developers.weixin.qq.com/miniprogram/product/record/guidelines`）只有三种：

| 类型 | 用在什么时候 |
|---|---|
| 新增备案 | 首次 |
| **变更备案** | 更新**已完成备案的**主体信息、小程序信息 |
| 注销备案 | 不做了 |

**改小程序名称 ⇒ 变更备案，不触发注销重备。**（这条常被说错成"改名要重新备案"。）

### 运营规范 5.35 原文要点

> **小程序名称变更**、小程序负责人变更、小程序主体名称变更、小程序主体负责人变更、
> 小程序或主体负责人联系方式变更时，都需要**及时变更备案信息**。

处理规则是**警告 → 封禁小程序功能 → 强制注销小程序备案**。
⇒ 顺序必须是：后台改名 → **名称审核通过** → **立刻**提交变更备案。
名称与备案信息不一致本身即违规，不能拖到"下次一起改"。

### 什么情况下必须「注销再重新备案」（不能走变更）

同一条 5.35 里写明两种：

1. 当前小程序主体的**统一社会信用代码与备案主体不同**（= 换主体了）
2. 备案主体**经营状态异常**（注销、吊销或撤销）

⚠️ 相关的一条云侧规则：**历史备案一旦锁定主体，无法通过"变更备案"改证件号**（MIIT 规则）。
所以主体选错的代价很高，**首次备案前把主体确定死**。

## 4. 命名：不能用裸词，必须「品牌 + 功能描述」

运营规范 2.5 原文要点：名称不能与已有小程序/公众号/热门应用重复或混淆，
**不能使用广义归纳类、普遍且不具识别性的词汇命名**；官方给的修改方向是
「品牌与产品描述或功能描述的结合」。

⇒ 裸两字通名（"照应""到家"这类）过不了。
⚠️ **查重只能在后台做**：微信在改名时实时比对已有小程序与公众号库，**站外查不到**，
只能登录后台试。取名阶段准备 5–10 个备选，别指望第一个就过。

另：名称/简介的**字符计数按 1 个中文 = 2 计**（简介上限 120 ⇒ 纯中文只能写约 56 字）。

## 5. 后台自动化姿势（mp.weixin.qq.com）

微信公众平台是 **wujie 微前端 SPA**，自动化要点：

- `fetch` 抓页面 HTML **全部返回同一个几 KB 的壳子** ⇒ 只能读
  `window.__INITIAL_STATE__` 或 `document.body.innerText`
- 合成 `dispatchEvent(new MouseEvent(...))` **一律无效**，必须
  `Page.bringToFront` + CDP `Input.dispatchMouseEvent`（trusted 事件）
- Playwright `connect_over_cdp` 会卡在枚举大量 tab ⇒ 用**裸 CDP over websocket**
- 表单页那个**字符计数器读不准**，判断有没有填进去要读 `input.value`
- 清 textarea：`Meta+A` 在 CDP 下选不中（Delete 只删一个字）⇒
  JS `el.focus(); el.setSelectionRange(0, el.value.length)` 再发一次**真** Backspace 键事件
- 某些表单页打开 ~5 秒会**自动 302 回引导页**，"页面消失"不等于填写失败 ⇒
  同一个脚本里完成"导航 → 填 → 读值"，别跨脚本分两次
- 验证是否真存到服务端**不能靠同标签页 reload**（Chrome 的 form restore 造成假阳性）⇒
  用 `Target.createTarget` 开新标签页读

通用的政务/控制台自动化铁律见 `automation.md`。

## 6. 只能人做的部分

企业认证的对公打款回填、管理员扫码确认（改名、部分配置变更）、
备案的主体负责人核验 —— 都要人。自动化能做到"把表单填好停在提交前"，最后一步交人。
